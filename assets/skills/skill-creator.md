# 技能创建器

一个用于创建新技能并对其进行迭代改进的技能。

在高层次上，创建技能的过程大致如下：

- 确定你希望该技能实现什么功能，以及大致如何实现
- 撰写技能的初稿
- 创建几个测试提示（prompts），并在这些提示上运行具备该技能访问权限的模型
- 帮助用户对结果进行定性和定量评估
- 根据用户对结果的评估反馈（以及从定量基准测试中发现的明显缺陷）重写技能
- 重复上述过程，直到满意为止
- 扩展测试集，并在更大规模上再次尝试

当你使用此技能时，你的任务是判断用户当前处于该流程的哪个阶段，然后介入并帮助他们推进到下一阶段。例如，用户可能会说："我想为 X 创建一个技能。"你可以帮助他们明确具体需求、撰写初稿、编写测试用例、确定评估方式、运行所有提示，并不断迭代。

如果用户已经拥有技能的草稿，可以直接进入评估/迭代环节。用户表示"不需要运行大量评估"时也可凭感觉来。

## 创建技能

### 捕捉意图

首先理解用户的意图。当前对话可能已经包含用户希望封装的工作流（例如"把这个变成一个技能"）。优先从对话历史中提取答案——所使用的工具、步骤顺序、用户所做的修正、观察到的输入/输出格式等。

1. 此技能应使模型能够做什么？
2. 此技能应在何时触发？（哪些用户语句/上下文）
3. 预期的输出格式是什么？
4. 是否需要测试用例？输出可客观验证的技能（如文件转换、数据提取、代码生成）适合测试；主观性强的技能（写作风格、艺术创作）通常不需要。

### 访谈与调研

主动询问关于边界情况、输入/输出格式、示例文件、成功标准和依赖项的问题。在这些问题理清之前，不要急于编写测试提示。

### 编写 SKILL.md

根据用户访谈结果，填写以下组成部分：

- **name**：技能标识符
- **description**：触发条件及功能说明。这是主要的触发机制——需同时包含功能说明以及具体的使用场景。让技能描述稍微"主动"一些：与其写"如何构建快速仪表板"，不如写"如何构建快速仪表板。只要用户提到仪表板、数据可视化、内部指标，即使没有明确要求'仪表板'，也务必使用此技能。"
- **compatibility**：所需工具、依赖项（可选，很少需要）
- 技能的其余部分

### 技能结构

```
skill-name/
├── SKILL.md (required)
│ ├── YAML frontmatter (name, description required)
│ └── Markdown instructions
└── Bundled Resources (optional)
 ├── scripts/ - Executable code for deterministic/repetitive tasks
 ├── references/ - Docs loaded into context as needed
 └── assets/ - Files used in output (templates, icons, fonts)
```

### 渐进式披露

技能采用三级加载系统：

1. **元数据**（名称 + 描述）- 始终在上下文中（约 100 字）
2. **SKILL.md 正文** - 技能触发时才载入上下文（理想情况下少于 500 行）
3. **捆绑资源** - 按需加载（无限制，脚本可在不加载的情况下执行）

**关键模式：**
- 保持 SKILL.md 少于 500 行；接近此限制时增加一层结构，并清晰指明模型下一步应读取哪个文件
- 在 SKILL.md 中清晰引用文件，并提供何时应阅读这些文件的指导
- 对于大型参考文件（>300 行），包含目录

**领域组织**：当一个技能支持多个领域/框架时，按变体组织：

```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
 ├── aws.md
 ├── gcp.md
 └── azure.md
```

### 无意外原则

技能不得包含恶意软件、利用代码或任何可能危及系统安全的内容。不要配合创建具有误导性的技能，或旨在促进未授权访问、数据窃取或其他恶意活动的技能。

### 编写模式

在指令中优先使用祈使语气。

**定义输出格式**：
```
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式**：
```
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

尽量向模型解释事情为何重要，而非生硬地使用陈腐的"必须"。先写出初稿，然后以全新的视角审视并加以改进。

### 测试用例

编写完技能初稿后，构思 2-3 个现实的测试提示——真实用户实际可能会说的话。与用户确认后运行它们。将测试用例保存到 `evals/evals.json`：

```
{
 "skill_name": "example-skill",
 "evals": [
 {
 "id": 1,
 "prompt": "User's task prompt",
 "expected_output": "Description of expected result",
 "files": []
 }
 ]
}
```

## 运行和评估测试用例

将结果放入 `<skill-name>-workspace/` 目录中，按迭代次数组织结果（`iteration-1/`、`iteration-2/` 等）。

1. 对每个测试用例，在同一轮次中启动两个子代理——一个带技能，一个不带技能（基线）。一次性启动所有任务以便同时完成。
2. 运行进行中时起草量化断言。好的断言具备客观可验证性，拥有描述性名称。
3. 运行完成后捕获计时数据（total_tokens、duration_ms）到 `timing.json`。
4. 评分、汇总并启动查看器：对每次运行评分并保存 `grading.json`；运行 `python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>` 生成基准报告。
5. 阅读反馈（feedback.json），空反馈表示用户认为结果没问题。改进重点放在用户有具体抱怨的测试用例上。

## 改进技能

1. **从反馈中归纳总结。** 目标是创建能适用于各种不同提示的技能，避免过度拟合少数示例。
2. **保持提示简洁。** 删除没有实际作用的内容。阅读完整对话记录，若发现技能导致模型浪费大量时间做无用功，尝试移除引发这些行为的部分。
3. **解释原因。** 解释你要求模型执行每项操作背后的**原因**。频繁使用全大写的 ALWAYS 或 NEVER 是警示信号——重新表述并阐明理由。
4. **寻找跨测试用例的重复工作。** 若所有测试用例都导致子代理编写类似辅助脚本，应将此脚本打包进 `scripts/` 目录并指示技能直接使用它。

改进技能后重新运行所有测试用例，输出到新的 `iteration-<N+1>/` 目录。持续迭代直到：用户表示满意 / 所有反馈为空 / 无法再取得实质性进展。

## 高级：盲测比较

当你希望对技能的两个版本进行更严格的比较时，可以使用盲测比较系统。
